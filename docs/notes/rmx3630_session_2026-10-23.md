## What was achieved today

1. **OPLUS DA2 auth layer defeated**: `oplus_security_verify_sec_policy`
   and `cust_security_verify_sec_policy` neutralized at runtime via
   heapbait's `CMD:EXP-PATCH-MEM`. The dummy SLA policy upload is
   ACCEPTED by the DA (`Server is not authenticated. Locked.` is gone).
2. **DA2 hash constraint established**: DA1 validates the DA2 image hash
   at boot (`DA Hash mismatch` + reset on every patched-binary attempt).
   All patching must happen on the RUNNING DA2, never in the binary.
3. **The OPLUS command-table gate decoded** (registrar at 0x40001a6c):
   `g_oplus_auth_status` decides which command table gets registered:
   - 3 (boot default) = LOCKED: basic table only (EFUSE r/w, GET-HW-INFO,
     READ-REGISTER); all flash commands answer `ERR!UNSUPPORTED`
   - 4 = read-back (read-only flash) table
   - 0/1/2 = FULL table (READ+WRITE flash/partitions)
   A bare `return 0` of the verifier leaves the status at 3 - the session
   lives but has no flash commands. The patch must ALSO store 1 into
   `g_oplus_auth_status` (0x4005455c on this build).
4. **A full GET-HW-INFO success was captured** (debug log session ~19:43):
   the DA returned the complete `da_hw_info` XML (UFS, block_size 0x1000,
   lua2 0x1dcb000000, product_id SG7DCQW8X8ONCI9T). Flash ops were still
   rejected at that time (status=3 table) - now understood and addressed.
5. **Root causes of the "random" EIO crashes identified**:
   - heapbait's generic `patch_da` mis-targets OPLUS functions (its
     hash_bind BL-chain lands on the OPLUS policy-table lookup 0x4002cbb4)
     and writes the DA.SLA patch using a FILE offset as a RAM address,
     clobbering preloader SRAM. Skipping it on OPLUS builds was necessary.
   - the OPLUS preloader CDC endpoint keeps emitting ASCII "READY" packets
     on bulk-IN even while the DA2 runs (caught: an xread header contained
     `52 45 41 44 59`). Any stray packet desyncs the XML protocol.
   - `.state`/`hwparam.json` cache in the working directory makes
     `DaHandler.connect()` skip the entire preloader handshake/DA upload
     and fire GET-HW-INFO at a fresh PRELOADER (instant EIO). Must be
     deleted before every attempt.
6. **Still open**: after SLA acceptance the DA2 stops answering the first
   GET-HW-INFO (silent hang / single EIO, then nothing). The current
   hypothesis is `get_hw_sbc` (0x40039d00): its stock code calls a bogus
   blx-thunk (an epilogue at 0x40031504) and effectively returns 1 ("SBC
   enabled") from garbage; GET-HW-INFO then enters a secure path that
   never answers. In the 19:43 session heapbait had force-returned this
   function and GET-HW-INFO worked - the patch is now replicated in the
   runtime set. **Not yet verified on the device.**

## Dead ends / reverted ideas (do not retry blindly)

- Pre-patching the DA2 binary before boot: impossible, DA1 hash check.
- `clear_halt()` after EIO: bulk data-toggle hazard; made sessions worse.
- Proactive EP_IN flush/peek before every header read: raced with the DA1
  boot right after the jump; consumed real packets. Only reactive flush
  after an actual failed response, discarding ALL pending data (the
  leftovers belong to the aborted response).
- Blind command re-send on empty response without discarding the aborted
  response first: desyncs permanently.
- Skipping the GET-SYS-PROPERTY roundtrip entirely (no warm-up exchange
  after the USB speed change): did not help by itself.
- `OPLUS_NO_USB_SPEED=1` (skipping change_usb_speed): the speed change /
  re-enum with fresh endpoint handles appears to HELP, not hurt; default
  is now to let it run.

"Security deny for [%s]" (printer 0x400084a4, ~130 generic callers -
do NOT patch the printer). Zero -> allowed.

0x40054314 (not the policy struct) - left alone for now.

## 23:5x-00:1x seccfg battle - final model (all verified against DA2 disasm)

### The DA never stores our seccfg bytes
Decisive observation: a restore of the ORIGINAL backup (V4, lock_state=4)
via full-partition WRITE-PARTITION came back as lock_state=2 (MP_DEFAULT,
new hash). The SEC service REGENERATES seccfg on every write with ITS OWN
state value - uploaded payload content is ignored (only the fact of a full
write matters). Small (512B) WRITE-PARTITION = erase + silent no-op; only
full-size padding commits.

### SEC state machine in DA2 (static)
- `sec_get_seccfg` @ 0x40034d6c - caches state in the global 0x4006E9F0.
- State WRITERS (the normalizer):
  - 0x40034ffc: `MOV r1,#1` (LOCKED path)
  - 0x40035014: `MOV r1,#2` (MP_DEFAULT path)  <- our state=2 came from here
  - 0x40035020: `STR r1,[r0]` -> [0x4006E9F0]
- `[SEC] set lock state as LOCKED` print site @ 0x4002ceac (func start
  0x4002c800, table-dispatched, no direct BL callers).
- "SECCFG Anti-Clone Enabled" string @0x510cb - seccfg is tied to the
  anti-clone/OTP layer; explains the paranoid regeneration behavior.
- "[SEC] set lock state as LOCKED" fix (commit 39ac1f3): BOTH writer MOVs
  patched to `MOV r1,#3` (LKS_UNLOCK) under OPLUS_WRITE_BYPASS:
  0x40035000: e3a01001 -> e3a01003, 0x40035014: e3a01002 -> e3a01003.

### Anti-tamper scrubber (WRITE-FLASH) - FINAL RULE
ANY WRITE-FLASH exchange touching the seccfg area - even one that hangs
BEFORE any data transfer - leaves the area ALL-ZERO afterwards (observed
4x). WRITE-FLASH/`wo`/`wf` on seccfg is FORBIDDEN forever. Only
WRITE-PARTITION (by partition name) is used for seccfg.

### Zero-recovery (commits 61bfd24 + f53fcdf)
`da seccfg unlock` no longer aborts on an all-zero seccfg: it builds a
fresh V4 payload WITHOUT parse (SecCfgV4 with hwtype="V4" - the hash comes
from the DA's own SEJ/HACC via custom_sej_hw), seeding ver/size/dm_verity/
sboot from /home/musin/seccfg_backup.bin header dwords (plain, no crypto;
verified: ver=4 size=0x3c dm_verity=0 sboot=0), create(lockflag) sets
state=3, pads to full 8MB, writes via WRITE-PARTITION.
Historical crash fixed: fresh SecCfgV4 has None fields -> struct.error in
create() (was hit twice, 2026-10-24 ~00:0x).
